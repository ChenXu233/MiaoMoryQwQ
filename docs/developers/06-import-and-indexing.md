- 状态：现行（如实描述 2026-09-06 时点行为，**含已知缺陷**，供所有者逐条裁决）

- 对应 UX 旅程：`docs/ux/user-journey.md`

## 1. 线程模型（谁在什么时候跑）

| 线程 | 数量 | 职责 | 生命周期 |
| :--- | :--- | :--- | :--- |
| Tauri 主线程 + WebView | 1+1 | UI 渲染、IPC 命令响应 | 常驻 |
| `mm-import` | 1 | 导入调度：按 chunk（32 张）切片、串行持久化、发进度事件 | 有导入任务时 |
| rayon 全局池 | **等于全部逻辑核心** | 每个 chunk 内并行执行：读盘 → SHA-256 → 解码 → 缩略图编码 | 常驻池，导入时吃满 |
| `mm-embed` | 1 | 每 1.5s 轮询「ready 但无向量」队列，32 张/组解码后按 8 张/批喂视觉塔 | 常驻，模型未就绪时空转 |
| 模型下载 | 按需 1 | 启动检查缺失自动下载（PR #5 起）；完成后加载模型并广播 | 下载期间 |

关键解耦事实：**导入管线对模型零调用**。嵌入（视觉塔推理）是独立后台线程异步补建的，与导入互不阻塞。这是刻意的架构决定（导入吞吐不被推理拖慢、模型可后补），但带来了 §4 列出的体验副作用。

## 2. 一张照片的完整旅程

```
【导入管线 mm-import + rayon】（每 chunk=32 张一批）
扫描枚举（跳过隐藏文件/不支持的扩展名，路径排序）
  → 整文件读入内存（std::fs::read，只读原文件）
  → SHA-256 全量哈希（去重主键）
  → 解码（image / libheif）+ EXIF 方向与拍摄时间
  → 缩略图：最长边 512px，WebP 无损
  → 串行持久化：exists_ready 查重 → insert_pending → 写缩略图 → mark_ready → 文件名入 FTS
  → 进度事件（每张一条）

【嵌入 mm-embed】（与导入异步，模型就绪后才开始）
  轮询 ready 无向量的资产 → 重新解码原图（注意：不是复用导入时的解码结果）
  → 视觉塔 int8 推理（8 张/批）→ 512 维向量写入 vec_assets
```

## 3. 对用户系统做了什么（隐私边界）

| 操作 | 是否发生 | 说明 |
| :--- | :--- | :--- |
| 读原文件 | 是 | 哈希与解码必需；只读打开 |
| 修改/移动/重命名原文件 | **否** | 管线中无任何写原路径的代码 |
| 复制原文件 | **否** | 不做副本，`storage_key` 存原路径 |
| 上传/联网 | **否** | 唯一网络行为 = 模型下载（spec 0004） |
| 写用户磁盘 | 是 | 仅工作区：`index.db` + `thumbs/*.webp`（口袋式布局见 ADR-0011） |
| 读 EXIF/GPS | 部分 | 仅读取 `DateTimeOriginal`（拍摄时间）与 `Orientation`（方向）两个字段；**GPS 坐标完全不读取、不入库**（`exif_json` 只含已取字段） |

## 4. 已知缺陷清单（D1~D8，待所有者逐条裁决，未获裁决不动代码）

| # | 缺陷 | 根因 | 影响 |
| :--- | :--- | :--- | :--- |
| D1 | **导入时全核饱和，机器卡** | rayon 默认线程数 = 全部逻辑核心，无并行度上限/优先级 | 导入期间前台应用明显卡顿（所有者实测确认） |
| D2 | **导入期间无法预览** | 时间轴只在「导入开始」和「导入完成」各 reload 一次，中间不刷新；而每张照片其实落库即可见 | 用户盯着空网格看几分钟，感知为"死了"（UX 侧最大缺陷） |
| D3 | **导入时模型零调用，"智能感"为零** | 嵌入与导入解耦 + 模型就绪依赖下载 | CPU 飞转却没有任何"AI 正在工作"的反馈；照片的向量滞后生成 |
| D4 | **内存峰值巨大** | 整 chunk（32 张）的**全尺寸解码图**同时驻留内存才串行持久化；一张 24MP RGB ≈ 72MB，峰值可达 2GB+；HEIC 更高 | 大图集导入有内存压力/换页风险 |
| D5 | 原图被解码两次 | 导入段解码一次（取缩略图）后丢弃；嵌入段为喂模型**再解码一次** | 同一张照片双倍解码成本（当时为解耦换取的简单性） |
| D6 | SHA-256 全量读盘无缓存 | 每次导入同一文件夹都完整重读重哈希（去重靠它兜底） | 重复导入慢；无 size/mtime 快速跳过机制 |
| D7 | 缩略图 WebP 无损偏大 | `image` 0.25 缺有损编码器（上游限制） | thumbs 目录体积大于必要值 |
| D8 | 嵌入进度语义粗糙 | `EmbedProgressEvent` 的 done/total 用"已嵌入/已就绪总数"近似 | 导入进行中 total 不断增长，进度条观感跳动 |

## 5. 当初为什么这样设计（诚实记录，供批判）

1. **吞吐优先**：白皮书 §5.3 写了「导入吞吐 > 50 张/s」的目标，rayon 全核 + chunk 并行是最短路径——但目标本身没有为"桌面前台体验"让路，这是目标设定的问题，不只是实现问题。
2. **嵌入与导入解耦**：P1 先交付无 AI 的导入浏览（ADR-0007 切片），P2 把嵌入做成独立 worker，避免两套管线互相阻塞——方向合理，但**补建的触发与反馈**没有设计好（D3）。
3. **预览缺失**：`pickFolder` 后 reload 一次是疏忽，不是权衡——数据层每张落库即可见，纯前端少做一个定时刷新/事件驱动 reload（D2）。
4. **全尺寸图驻留**：为把"查库不进并行段"（SQLite 非 Sync）的约束做简单，解码结果整 chunk 攒着，没想到内存量级（D4）。

## 6. 修复方向候选（仅列出，等裁决；未获裁决不动代码）

- D1：rayon 线程数可配置 + 默认留 2 核给系统；或提供「后台模式」低优先级
- D2：导入中每 chunk 完成即通知前端增量 reload（或 SSE 风格增量事件）
- D3：导入启动时若无模型 → 明确的"索引将在模型就绪后自动补建"状态卡（而非静默）
- D4：解码→缩略图→持久化改为单张完成即释放（流式化 chunk），峰值降到 1~2 张全尺寸图
- D5：导入时把缩略图大图直接喂嵌入（512px 本来就是 CLIP 预处理上采样前的合理输入），省一次原图解码——需基准确认精度无损
- D6：size+mtime 指纹快速跳过（ sacrifices 严格哈希去重，需权衡）
- D7：等上游有损编码器 / 换 mozjpeg 或 ffmpeg（与 ADR-0008 冲突，需新 ADR）
- D8：嵌入进度改为"本轮队列完成数/本轮队列总数"
