# ADR-0002：保留 sqlite-vec 作为向量索引

- 状态：Accepted
- 日期：2026-09-04
- 决策者：项目所有者
- 相关：白皮书 §3.2、§4.2、§8

## 背景

v0.1 白皮书已选定 sqlite-vec。评审中曾提出"SQLite BLOB + 内存暴力扫描"替代方案，理由是规避 C 扩展的打包与上游维护风险。项目所有者最终裁定：保留 sqlite-vec。

## 决策

我们决定：

1. **保留 sqlite-vec 作为唯一向量索引**，KNN 索引 + 分区键（year）+ INT8 量化策略不变。
2. **不自研任何检索算法**："BLOB + 内存暴力扫描"视同自研方案，被否决——索引与检索是数据库的职责，我们不做第二套算法，也不维护第二套优化路径。
3. 封装在 `VectorIndex` trait 之后（ADR-0005），SQLite 事务内与元数据同库写入。
4. 版本锁定 sqlite-vec；每次发版复查上游提交动态，结果记入风险表（白皮书 §8）。
5. escape hatch 仅作风险预案：usearch / sqlite-vector（社区延续版）/ PG+pgvector，当前不实现。

## 后果

### 积极

- 检索算法、索引优化（KNN/分区/量化）由成熟扩展承担
- 向量与元数据同库，事务一致性好，可剥落性不降
- 我方代码更简洁：只写查询，不写算法

### 消极 / 需关注

- 需处理 vec0 限制：更新 = 删除 + 重插；元数据外置；WAL 备份需 checkpoint
- 上游维护状态需持续监控（列入发版检查清单）

## 备选方案

| 方案 | 结论 | 原因 |
| :--- | :--- | :--- |
| BLOB + 内存暴力扫描 | 否 | 需自行维护算法、优化路径与并发正确性，复杂度和维护成本反而更高 |
| usearch（Rust 绑定） | 否 | 脱离 SQL，双存储一致性与备份复杂度上升 |
| sqlite-vector（社区延续版） | 观察 | 作为上游停更时的首选逃生通道 |
